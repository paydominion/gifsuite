# GifSuite for iOS — Swift feature plan

Baseline: 2026-09-30. This is a source review of the current working tree, not a runtime or release certification. The web roadmap is `../ROADMAP.md`; executable routes, UI and tests take precedence when its descriptions are stale.

## Product and architecture

Build a native SwiftUI companion to GifSuite: grab GIFs from X and supported web links, browse the public feed, save and share media, and use the same conversion and editing tools as the web app. Keep iOS 17 as the deployment target and retain the existing Grab, Tools, Timeline and Settings tabs.

Use the existing `@Observable`, `@MainActor` view models, typed `Codable` models and async `URLSession` services. Add injectable networking, file upload/download support and feature-specific services as needed. Use native media pickers, Files export, a share sheet and AVKit playback. Treat these as implementation choices to validate against the SDK when each feature is built.

Reuse the Cloudflare API and media processor. X extraction, format conversion, compression, storage, moderation and editing pipelines remain on the server; caption rasterization is client-side. Swift owns navigation, touch controls, previews, request state and export. Do not embed server secrets or duplicate ffmpeg processing in the app.

## Existing implementation

- `Sources/App/`: app entry, four tabs and a navigation stack per tab.
- `Sources/Core/Networking/`: JSON GET/POST client; feed and grab endpoints.
- `Sources/Features/Grab/`: submission, progress and success/error text; no result screen navigation.
- `Sources/Features/Timeline/`: initial feed, poster cards and pull to refresh; no pagination, playback or detail screen.
- `Sources/Features/Tools/`: informational rows only; conversion and compression are not implemented.
- `Sources/Features/Settings/`: server and app version display.
- `project.yml`: iOS 17, iPhone/iPad, staging API configuration. The design adaptation builds successfully for the iPhone 17 Pro simulator (iOS 26.2); physical-device acceptance remains pending.

## Multiple-source grab (IOS-17)

The working tree now routes embedded X posts and X/t.co hosts through the existing X resolver, and other HTTP(S) links through `extractLink` and the processor. Generic extraction takes the first web link (or a scheme-less domain with a path) and trims trailing pathname punctuation. Direct GIF/MP4/WebM media, page link-preview media and public pages understood by yt-dlp are attempted; there is no published capability list guaranteeing every named site. The private-address, unavailable, login-required and unsupported-media responses should remain actionable server errors. Native Swift should submit the text to the existing grab endpoint, keep it editable on failure, and avoid duplicating extraction or performing server fetching on-device.

For HTML pages, `mediaFromHtml` extracts Open Graph video and Twitter player-stream URLs first, preferring MP4, then GIF image URLs; it skips candidate paths ending in WebP. Relative links resolve against the fetched page URL. The processor tries at most four ranked candidates and one HTML meta-refresh page when there are no candidates, then falls back to yt-dlp if no file was selected. Candidate fetches use the existing URL/redirect checks and byte cap. An initial 404/410 is terminal; other unsuccessful page responses can fall back to yt-dlp, so a source-site HTTP 403/429 does not directly dictate the public API status. Existing grab JSON and native error handling remain unchanged.

Successful tag extraction uses the page title and `og:site_name` as uploader metadata, retaining the submitted page link. This path does not populate `ageLimit`; automatic site-labelled sensitivity applies only when the processor actually returns a rating of at least 18 (currently yt-dlp metadata). Direct/tag-derived media starts unchecked unless another verdict exists; public items await scanning and private items await becoming public. The roadmap/checklist’s blanket adult-site blur statement is an acceptance goal, not current proof. IOS-26 must honor the returned `nsfw` state and never infer a sensitive verdict from the hostname or a request succeeding.

`migrations/0003_grab_sources.sql` adds `source`, default `x` for existing rows. Feed GIF objects now expose `source: string` (`x` or a site hostname). For non-X rows, legacy field names remain: `tweetId` is `url:` plus a normalized-link hash, `tweetUrl` is the source page/file, `tweetText` is the title, and author fields use uploader metadata or a site-name fallback. They are not guaranteed to represent a tweet or X handle. `Gif.swift` currently ignores `source` without a decode failure, but `GifCard.swift` still uses “GIF from X” for an empty title. Add source-aware models/copy; reserve @handle and X-like counts for X, show author/site for other sources, and open the provided source URL. CORE-03 must carry the same attribution and source URL for arbitrary-ID detail; no JSON detail endpoint was added.

Non-X origin lookup returns HTTP 200 `{available:false, mediaUrl:null, reason:"not-from-x"}`. Treat this as a different sharing mode, not a deleted X post: offer canonical page-link sharing and optional-caption X intent using that page URL, plus file export for attachment. The web emits `x-link` for this action, retains `x-original` for supported X embeds and `copy-link` for copying. Do not promise original-author credit or inline playback for non-X links; sensitive-content preview restrictions still apply. X origin responses retain their existing shape, so decode `reason` as optional and tolerate future values.

Non-X deduplication uses the normalized submitted link with media index 0. It forces HTTPS for the key, strips selected mobile/www prefixes, fragments and tracking parameters, sorts remaining query parameters and removes trailing slashes. This preserves existing ownership/visibility on repeated equivalent links, but is not cross-site, redirect-target or media-fingerprint matching; IOS-21 remains future backend work. Normalized keys are server internals, not native IDs to construct. A processor-returned source age rating of at least 18 produces a sensitive verdict with source `site`; the same private/pending/safe/sensitive feed rules and owner controls apply.

Backend dependencies are the new migration, processor `/fetch` implementation and container including `fetch.mjs`, yt-dlp and ffmpeg. The internal endpoint normalizes accepted files to H.264/AAC MP4 with even dimensions; existing poster/download paths remain in use. It is not a new public API for Swift. Grab defaults remain 50 MiB source size and 60 seconds, controlled by server configuration, separate from the 25 MiB upload-tool default. The current sniffing branch rejects all WebP input with the animated-WebP error, so do not promise static WebP link support either. Link failures map to 400 malformed/private-address, 403 sign-in-required, 404 gone, 413 size/duration, 415 wrong format/WebP, 422 missing/undecodable media and 502 source failure; existing 429/500 handling still applies.

`ROADMAP.md` now marks more-site grabbing built on 2026-10-03, awaiting human testing, within phase 4. This is source/readiness evidence, not verified deployment or native completion. Tests added during review now cover generic-link extraction/normalization, direct-file/page grabs, attribution, normalized repeats, source-labelled sensitivity, limits, format/login errors, public-address/redirect rejection and the non-X origin reason (`tests/unit/links.test.ts`, `tests/api/links.spec.ts`). `tests/fake-x/server.mjs` supplies file/page fixtures and `tests/fake-ytdlp.mjs` supplies page metadata; these do not validate real-site yt-dlp behavior. Existing API/e2e tests have also adopted the generic input labels and missing-media error. Full non-X sharing/browser acceptance and real-site staging checks remain required; no passing run or fixture wiring was verified by this sync. Non-web schemes without an embedded HTTP(S) link are explicitly rejected by `extractLink`. No targeted `mediaFromHtml`/tag-fetch/meta-refresh fixtures were found in the reviewed tests; add them alongside the existing yt-dlp-based page fixtures. TESTING.md now provides a real-site checklist for Giphy, Tenor, direct GIF, Reddit/TikTok, deduplication and non-X sharing; those checks are not recorded as passed here.

## Pasted links and analytics

IOS-01 now accepts surrounding text through the existing `POST /api/grab` string field `url`; its response remains `{id, created, public}`. `lib/x/fetchTweetMedia.ts` prefers an embedded supported X/Twitter post link, including supported alternate hosts and media-slot paths, before trying the first HTTP link. Preserve the text apart from outer whitespace and let the server extract the post; stricter whole-string URL validation in Swift would reject supported input. The X parser still rejects unsupported/lookalike hosts, but the public grab dispatcher now sends non-X hosts through the generic link fetcher (IOS-17); they are no longer universally rejected with an “Only X” error. Bare `https://t.co/...` and scheme-less `see t.co/...` receive guidance to open the short link and copy the post’s X URL; this is not automatic short-link resolution. Other wrapped short-link forms can still receive the generic unsupported-site error, so display the actual server message. Reference: `tests/unit/parseTweetUrl.test.ts`. The current GrabViewModel already forwards trimmed text, but native fixture/device acceptance is not recorded.

IOS-27 tracks the new analytics integration. `lib/analytics.ts` adds Workers Analytics Engine writes alongside existing D1 events. Download/convert/compress wrappers record status, timing, options and header-derived byte counts; grab records selected outcomes and source hostname; accepted view/share/report and visibility changes, moderation and admin operations have explicit event calls. This is not every API call: feed/origin reads and several early validation/auth failures have no new event. Unset numeric fields default to zero, so zero does not necessarily mean a measured zero-byte transfer or an HTTP status. The writes catch binding/write failures; native request success must not depend on analytics delivery. Since 2026-10-21 the Worker also logs qualifying GET page views as `page` events with route path, source/referrer or crawler, status and duration; API, media, assets and prefetch requests are excluded (robots and sitemap are included).

Request context includes country, a coarse User-Agent device class, and the existing daily visitor hash derived from IP, User-Agent, day and server salt; raw IP and full pasted URLs are not analytics fields. `siteOf` extracts a hostname independently of the supported-post parser, so mixed-link text can report a different host from the chosen X post. The existing `POST /api/events` now also accepts browser-only GIF-less `{type: "ui"|"client_error", detail, path?}` events: analytics only (not D1), 60/minute per IP, link-redacted and whitespace-normalized detail capped at 96 characters, and a leading-slash path with query/fragment removed and a 64-character cap. The browser reports file kinds, rejected files, shown errors and JS failures (at most 10 events/page). Its client scrub covers known media filename extensions; server URL redaction is not general personal-data scrubbing. Do not send raw pasted text, filenames, credentials or arbitrary user text from Swift. Keep native events to intentional view/share/report actions; there is no native page-view beacon or new native telemetry requirement.

The existing manual backlog asks for a descriptive native User-Agent. Define a stable app/version value with the actual `iPhone` or `iPad` family token in CORE-01, and verify it: `deviceOf` recognizes those tokens, whereas an `iOS` label alone falls through to desktop. The current schema records only the coarse class, not a distinct app/version dimension; recognizing native-app sessions separately needs a backend schema change. `APIClient.swift` currently sets no explicit User-Agent.

`components/shell/WebAnalytics.tsx` remains a separate optional browser beacon for Core Web Vitals when a valid public site token is configured; Worker page events do not depend on that token. No Swift screen-view beacon or extra CSP header is required. Deployment configuration adds separate Analytics Engine datasets; `DEPLOY.md` keeps reporting credentials operator-only and the Web Analytics token optional for Core Web Vitals. Existing and changed tests cover field layout/classification, page filtering/referrers/crawlers, GIF-less event status and representative browser flows (`tests/unit/analytics.test.ts`, `tests/api/events.spec.ts`, `tests/api/security.spec.ts`, `tests/e2e/app.spec.ts`, `tests/e2e/convert.spec.ts`, `tests/e2e/shell.spec.ts`). They are coverage intent only; this sync did not run them or verify Analytics Engine delivery or deployment.

## Positioning, visibility and sensitive content

The web hero no longer presents GifSuite as an X-only product: the eyebrow is "The all-in-one GIF suite" and the headline "Grab, convert and make GIFs." The new draft grab flow also accepts non-X links (IOS-17); “anywhere” in web copy is not verified support for every site. `Sources/Features/Grab/GrabView.swift` still shows "The GIF suite for X" and should follow when native work is next requested.

Grabbed GIFs are now public by default, with a "Show on the public timeline" checkbox before grabbing (web; a native Toggle remains acceptable per iOS convention) and a switch, for the grabber only, on the GIF page. Private means unlisted: off the feed, with a `noindex` directive for search engines. The page, media, downloads and link previews remain accessible to anyone with the link; this is not account-based access control. The sensitive-content check gates the feed only; grab, download and share never wait for it. X's "possibly sensitive" mark is applied at grab time. Otherwise a public GIF starts unchecked (`nsfw: null`, off the feed, not blurred) and is scanned in the background; a private one is scanned when made public; a server cron retries unfinished checks. Sensitive GIFs never appear in the feed, have no link-preview image, and show blurred with "Show the GIF"; downloads still work. Native UI must not wait for or poll the check after grabbing. Admins can override with `POST /api/admin/nsfw` (server-only; never in the app).

`nsfw` is a three-state value: null means unchecked, false means allowed by the current server verdict, and true means sensitive. Do not treat null as sensitive or safe, or infer a verdict from feed absence. On sensitive detail, match the web gate by withholding the video/player until an explicit “Show the GIF” action, with an accessible cover and reveal control. Show the web’s new notice that only visitors aged 18 or older should continue before the reveal action. This is explanatory UI, not a server-verified age or consent contract; no age field or verification endpoint was added. Reset reveal state for a different GIF. Private and unchecked web pages retain link previews; sensitive pages omit preview media and tweet text from metadata. Hidden/taken-down content remains a separate unavailable state.

The owner cookie is issued only when a client without a valid key creates a new GIF. It is HttpOnly, SameSite=Lax, path `/`, valid for one year and Secure over HTTPS. A repeated grab changes neither ownership nor visibility, and cannot recover a lost key. The native app must test cookie capture, reuse and relaunch persistence with the configured API host; do not assume Safari and URLSession share ownership. Migration `0002_visibility_nsfw.sql` leaves old GIFs public with a legacy safe verdict and no owner key; these were not newly scanned.

Backend dependencies are the migration, processor dependencies/model in `processor/package.json` and Dockerfile, post-response scanning, and the five-minute retry cron with a configured admin token. Their presence in source does not establish deployment or a scan completion deadline. The scanner samples up to six frames and uses the highest explicit score, default threshold 0.6; X's sensitive mark (or yt-dlp age limit of at least 18) takes precedence. The sweep retries public, visible, unchecked items; scan failure leaves null and later scans do not overwrite existing X/site/admin verdicts. These are server responsibilities, not a native model or admin API integration.

The additive response fields remain decodable by the current Swift models, but the behavior invalidates `GrabView.swift` (“Every grab joins the public timeline.”) and `GrabViewModel.swift` (“GIF added to the timeline.” / “That GIF is already in the timeline.”). `GifService.swift` sends only `url`, so it currently defaults to public; `GrabResponse` ignores the returned `public` value. Prioritize accurate saved-result copy and visibility selection. Grab does not return the scan verdict: open the result immediately, without promising feed placement, classifying the result locally or polling a nonexistent scan-status endpoint.

- Convert/Compress uploads accept GIF, MP4/MOV and WebM; WebP remains output-only for those tools. Maker has a separate JPEG/PNG/WebP/GIF image validator; still WebP maker support does not enable animated WebP link grabbing or conversion. Check the distinct validators in `lib/media/sniff.ts`.
- Compression UI currently offers 15, 10, 5 and 1 MiB plus custom. The roadmap's Discord 8 MB description is stale. These are current product presets, not independently verified platform limits.
- Upload and duration defaults are 25 MiB and 60 seconds, configurable on the server. Do not present them as immutable client limits. A capability/config endpoint would avoid drift.
- Error statuses include 400 validation, conditional human-check 403 on grab/upload/edit routes, 413 size/duration, 415 unsupported type, 422 damaged input, 429 rate limit, 503 processor updating and 500 failure. Preserve HTTP status in Swift; do not decode a binary success as JSON.
- A JSON detail endpoint and a capabilities endpoint are proposed dependencies, not existing routes. CORE-03 must include `source`, source-page URL/attribution, `isPublic`, nullable `nsfw` and a server-derived permission to manage visibility, without exposing owner keys/hashes. The permission field name/route are not yet defined. Feed metadata cannot retrieve private, unchecked or sensitive GIFs. Direct-link and grab-result detail must wait for this contract or explicitly use the web page fallback; that fallback may not share the app’s owner cookie.

## Definition of native parity

A feature is complete only when its Swift screen/service exists, relevant success and failure paths pass, and human device acceptance is recorded. A placeholder row, web roadmap tick or successful build alone is insufficient. Preserve status and evidence separately for web and iOS.

Native QA includes Files/Photos access and cancellation, large media memory use, background/interruption behavior, unsupported previews with export still available, Dynamic Type/VoiceOver, dark mode, iPhone/iPad layouts, no duplicate submissions/events, and hidden/deleted content. For changes to shared web code, retain the repository's existing `npm run check` and end-to-end requirements.

The actionable work is in `BACKLOG.md`. Ongoing updates follow `SYNC.md`.
